A1. Appendix — SQS & DLQ specifics

1 Overview

This service runs delayed HTTP callbacks for other Verba services. A caller sends one request: "here is a url, a payload, a jobId, and a delay in seconds — POST that payload to that url after the delay." The service saves the job in MongoDB, and later makes the HTTP POST at the right time. That is the whole job.

Three parts do the work together:

  • Schedule API (services/scheduler/) — takes the request, locks the jobId in Redis, and upserts the job into MongoDB with status scheduled.
  • Once-a-minute cron (crons/job_processor.cron.ts → triggerCallbacks) — finds jobs that are due soon, marks them inProgress, and puts each on SQS with a delay so SQS delivers it close to the exact due time.
  • SQS consumer (sqs/consumers/job_processor/ → handleJob) — reads a job off the queue, checks it is still the current version and not cancelled, makes the HTTP POST, and marks the job success or failed.

Why two paths (cron + an immediate enqueue inside the schedule call)? The cron scans in one-minute windows. A job scheduled with a short delay, right after a window already passed, would sit unseen until... never. So the schedule call also enqueues the job straight away when it falls inside a window the cron has already claimed. See §13.

3 High-level design

Three planes: the schedule call (write the job), the cron (find due jobs and queue them), and the consumer (fire the callback). SQS sits in the middle and does the actual waiting via DelaySeconds.

The one spot that most often bites: the cron has no overlap guard (§6, §13) and the job collection has no indexes (§7). Both are quiet until load grows.

4 Sequence diagrams

4a. Schedule a job

Steps 3–5 run inside retryWithBackoff (3 tries) for infrastructure errors. Step 5 (dashed) only fires when the job lands in a window the cron already claimed.

4b. Cron trigger — triggerCallbacks, once a minute

  1. Read the last completed run → startTime = its endTimeStamp. If none exists, fall back to the hard-coded bootstrap date 2025-10-07 (§13).
  2. endTime = now + 60s (THRESHOLD_SECONDS).
  3. Find scheduled jobs with callbackTime in (startTime, endTime].
  4. In parallel: create a new run row (status inProgress, endTimeStamp = endTime) and bulk-mark those jobs inProgress.
  5. Enqueue each job to SQS with DelaySeconds = callbackTime - now (floored at 0). Failures are logged per job via Promise.allSettled, not thrown.
  6. Mark run rows with endTimeStamp >= startTime and status inProgress as completed.

4c. Consumer — handleJob per SQS message

  1. Parse {jobId, version}. Look up the job by jobId. Missing → log + return (message later deleted).
  2. Version guard: if the message version ≠ the job's current version → return (a newer schedule replaced this one). §13.
  3. Cancel guard: if status is cancelled → return.
  4. HTTP POST url with payload, headers x-idempotency-key: jobId and job_id: jobId, 10s timeout. axios-retry does up to 3 tries on 5xx/429/network.
  5. Success → mark success, delete the SQS message. HTTP failure (AxiosError) → mark failed, delete the message (no consumer-level retry). Infrastructure error → re-throw so the outer retry/redelivery handles it.

5 Event processors (SQS consumer)

Started by startAllConsumers() only when SHOULD_RUN_CONSUMERS === 'true'. Uses the sqs-consumer library with handleMessageBatch, batchSize: 10. Deletion is manual — the batch handler returns undefined, so the library does not auto-delete; the code sends its own DeleteMessageCommand.

8 External deps & secrets

  • MongoDB — the only datastore. Connection string in MONGO_URI. Holds both collections above.
  • Redis — used only for the per-jobId schedule lock (SET NX EX). Config: REDIS_HOST, REDIS_PORT, REDIS_USERNAME, REDIS_PASSWORD.
  • AWS SQS — the delay queue. Queue URL in SQS_JOB_PROCESSOR_URL. Credentials via AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY, region AWS_REGION (default eu-west-2). A DLQ is expected behind an SQS redrive policy (configured in AWS, not in code).
  • AWS Secrets Manager — optional. When USE_AWS_SECRETS=true, initConfig loads AWS_SECRETS_ID and fills env vars that are not already set (local .env wins).
  • OpenTelemetry → Jaeger — traces via OTLP HTTP. Endpoint from OTEL_EXPORTER_OTLP_ENDPOINT / JAEGER_ENDPOINT (default http://localhost:4318/v1/traces).
  • Downstream callback targets — any URL a caller passes. This service will POST to whatever url it is given. There is no allow-list.

9 Per-client / multi-tenant quirks

  • This service is client-agnostic. There is no client code, no per-client config, and no per-client branching anywhere in the code. It stores a URL and a payload and calls the URL. Any multi-tenant meaning lives entirely in the caller's url and payload.
  • The source field in the schedule request looks like it should say who owns the job, but it is dropped — not validated, not written to Mongo. If you need to attribute jobs to a caller or client, you must add persistence for it first.
  • retryCount is passed into createOrUpdateJob too, but the schema does not define it, so it is also silently dropped.

11 Runbook (debug / ops)

  • Find a job: in Mongo, db.scheduled_internal_job.findOne({jobId}). Look at status, callbackTime, version, updatedAt.
  • Stuck in scheduled (never fired): the cron is not running or SHOULD_RUN_CRONS is false. Check the latest internal_job_run_details row — is a new one being created each minute? Check logs for jobProcessorCron started / completed.
  • Stuck in inProgress: it was enqueued but the consumer did not finish. Check SHOULD_RUN_CONSUMERS, the SQS queue depth, and the DLQ. Look for started processing job and either job processing failed... line.
  • failed job: the HTTP callback failed after 3 axios retries. Grep HTTP callback failed after axios retries with the jobId; the log carries the target url. Check the target service's health.
  • Re-run a job safely: POST /api/v1/scheduler again with the same jobId. The upsert bumps version, resets status to scheduled, and orphans any old in-flight SQS message (the version guard drops it). This is the clean way to retry.
  • Messages in the DLQ: those exhausted infrastructure retries. Fix the infra cause, then redrive the DLQ back to the main queue. Delivery is idempotent enough because of the version + status guards.
  • Where to look: logs are structured Pino JSON with a requestId per request/message. Traces go to Jaeger under service name job-scheduler-service.

13 Gotchas / why / tribal knowledge

The version number is the whole dedup trick
WHY: every schedule/re-schedule does $inc: {version:1}. The SQS message carries the version at enqueue time. handleJob compares it to the job's current version and drops the message if they differ.
WHAT BREAKS: stop bumping version, or stop checking it, and duplicate/stale messages will fire the callback more than once. This is also why re-scheduling with the same jobId is the safe retry.
The schedule call sometimes enqueues immediately
WHY: the cron scans in 60s windows and records each window's end. A job scheduled with a short delay can land inside a window the cron already finished — the cron will never look there again. So if callbackTime <= latestRun.endTimeStamp, the schedule call marks it inProgress and enqueues it right away.
WHAT BREAKS: remove this and short-delay jobs scheduled just after a cron tick are silently dropped — they are neither in a future window nor picked up again.
Hard-coded bootstrap date 2025-10-07
WHY: the very first cron run has no "last completed run" to start from, so triggerCallbacks falls back to moment('2025-10-07') as the window start.
WHAT BREAKS: if internal_job_run_details is ever wiped, the next run rescans from 2025-10-07 and could re-pick very old scheduled jobs. Also, any job with a callbackTime before that date would never be picked by a fresh run. It is a magic value — treat it carefully.
THRESHOLD_SECONDS must equal the cron cadence
WHY: the cron runs every minute and looks 60s ahead. The two numbers are one setting split in two files (constants.ts and the cron expression).
WHAT BREAKS: threshold < cadence → gaps where due jobs are missed. Threshold > cadence → the same job's window is scanned by two ticks → double enqueue.
SQS DelaySeconds has a hard ceiling of 900s (15 min)
WHY: today this is safe only because the cron enqueues jobs due within 60s and the immediate-enqueue path only fires for jobs already inside a past window (delay near 0). So the computed delay is always small.
WHAT BREAKS: raise THRESHOLD_SECONDS above 900, or add any path that enqueues a far-future job directly, and SQS rejects it with InvalidParameterValue. The code does not cap the delay.
Cancel does not lock and does not bump version
WHY: cancel just sets status to cancelled. It relies on the consumer's status check to skip the job. Leaving the version unchanged is deliberate — the in-flight message's version still matches, so the status guard is what stops it.
WHAT BREAKS: note that CLAUDE.md claims cancel uses the Redis lock — it does not. A cancel racing with a re-schedule is not serialized, so last-write-wins on status. Usually fine, but know it before you rely on ordering.
updateRunStatus is broad. It marks every inProgress run with endTimeStamp >= startTime as completed, not just the row this tick created. With no overlap guard, two overlapping cron runs can mark each other complete. Combined with the missing indexes, this is the area to harden first if load grows.

14 Known bugs & tech debt

  • No indexes anywhere. Every query is a full collection scan. Add (status, callbackTime) and a unique jobId on scheduled_internal_job, and (status, createdAt) on internal_job_run_details.
  • jobId is not unique. Correctness rests on the Redis lock alone. A unique index is the durable guard.
  • No cron overlap guard. Plain node-cron, no max_instances, no distributed lock. Overlapping runs can double-enqueue. Add a run lock or an "is a run already in progress" check.
  • No cleanup / TTL. Both collections grow forever. internal_job_run_details adds ~1,440 rows/day. Add a TTL or an archival job.
  • Hard-coded bootstrap date 2025-10-07 in triggerCallbacks — a magic value, fragile if run-details is wiped.
  • source and retryCount are accepted but dropped — not in the schema, never persisted. Either wire them in or remove them from the request type.
  • No auth on the endpoints. Anyone who can reach the pod can schedule a POST to any URL (SSRF surface, since there is no URL allow-list).
  • Logging key mismatch in handleJob's version-mismatch log: it sets num_key2: 'current version' but then writes the value under num_key3_value, so the current version is not logged under the right key.
  • Enqueue-failure jobs get orphaned. If SQS enqueue fails inside the cron, the job is already marked inProgress, so the next tick (which only looks at scheduled) will not retry it.
  • No test suite. npm test is a no-op. All external deps (Mongo, Redis, SQS, HTTP) must be mocked when tests are added.

15 How to test locally

No automated tests exist. To exercise the flow end to end on a laptop, you need MongoDB, Redis, and an SQS-compatible queue (LocalStack works).

A1 Appendix — SQS & DLQ specifics

  • Message body: just {jobId, version} as JSON. The url and payload are read from Mongo at consume time, not carried on the message — so a re-schedule between enqueue and consume is always respected.
  • DelaySeconds: computed as callbackTime - now (floored at 0). SQS's max is 900s; the design keeps it well under that (§13).
  • Consumer: sqs-consumer, batchSize: 10, handleMessageBatch. Messages are deleted manually via DeleteMessageCommand; the handler returns undefined so the library does not auto-delete.
  • Retry split: infrastructure errors → retryWithBackoff 3× (500ms base, ×2 growth, 2s cap, up to 150ms jitter) then left for redelivery. HTTP/app errors → deleted immediately, job marked failed.
  • DLQ: handled by the SQS redrive policy (set in AWS, not code). A left-behind message is redelivered until maxReceiveCount is hit, then moved to the DLQ.
  • Credentials + region: sqsClient.ts reads AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY and AWS_REGION (default eu-west-2).
